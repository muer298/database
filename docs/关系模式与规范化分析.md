## 一、E-R 模型到关系模式的转换

### 1.1 转换规则

依据概念结构设计产出的 E-R 图，按以下规则转换为关系模式：

1. 每个实体转换为一个关系模式，实体的属性成为关系的属性，实体的码成为关系的码；
2. 1:N 联系不单独建表，在「N」端关系中加入「1」端关系的码作为外键；
3. M:N 联系必须转换为一个独立的关系模式，其码为两端实体码的组合，联系自身的属性也一并纳入；
4. 1:1 联系可在任一端关系中加入另一端码作为外键（本系统无此情形）。

### 1.2 转换结果

E-R 图中共有 7 个实体和 8 个联系。其中「放映场次 — 座位」为 M:N 联系，按规则 3 转换为独立的第 8 张表——「有效座位占用 seat_occupancies」。其余联系均按规则 2 以外键方式融入对应实体表。

| 序号 | 关系模式（逻辑名） | 物理表名 | 来源 | 类型 |
| --- | --- | --- | --- | --- |
| 1 | 用户 User | `users` | 实体 | 实体表 |
| 2 | 电影 Movie | `movies` | 实体 | 实体表 |
| 3 | 影厅 Hall | `halls` | 实体 | 实体表 |
| 4 | 座位 Seat | `seats` | 实体 + 影厅1:N | 实体表（含外键） |
| 5 | 放映场次 Screening | `screenings` | 实体 + 电影1:N + 影厅1:N | 实体表（含外键） |
| 6 | 订单 Orders | `orders` | 实体 + 用户1:N + 场次1:N | 实体表（含外键） |
| 7 | 电影票 Ticket | `tickets` | 实体 + 订单1:N + 场次1:N | 实体表（含外键） |
| 8 | **有效座位占用 SeatOccupancy** | `seat_occupancies` | **场次 M:N 座位 联系转换** | **联系表** |

### 1.3 多对多联系的转换说明（核心）

「放映场次」与「座位」之间存在 M:N 联系：一个场次包含多个座位，一个座位可被多个不同场次使用。若仅在场次表或座位表单侧加外键，都无法完整表达这种联系，更无法记录「某场次下某座位是被锁定还是已售出」。

因此将其转换为独立关系模式：

> seat_occupancies（**screening_id**, **seat_id**, order_id, occupancy_status, locked_at, lock_expires_at, updated_at）

- 主码为（screening_id, seat_id）的组合，天然保证「同一场次的同一座位只有一条占用记录」，从数据结构层面杜绝重复售票（对应业务规则 BR-02）。
- 「占用状态」occupancy_status 是联系自身的属性，取值：`AVAILABLE` / `LOCKED` / `SOLD`；退票时由 `SOLD` 恢复到 `AVAILABLE` 并清空当前 order_id，不设独立的「已释放」状态。
- 增加 `lock_expires_at`（锁定过期时间）支持锁定超时自动释放，`updated_at` 记录最后变更时间。
- 该设计同时解决了「同一物理座位在不同场次状态不同」的建模难题。

## 二、关系模式清单（8 张表）

> 记号约定：**加粗**为主码属性，`FK` 标注为外键，`UK` 标注为唯一约束。属性使用中文别名便于阅读，括号内为物理列名（snake_case），以 `sql/create_tables.sql` 为准。

### R1 用户（users）
用户（**用户ID** `user_id`, 用户名 `username` `UK`, 密码哈希 `password_hash`, 真实姓名 `real_name`, 手机号 `phone` `UK`, 邮箱 `email`, 角色 `role`, 注册时间 `registered_at`, 账户状态 `account_status`）

- 主码：user_id；候选码：username（phone、email 可空，仅作为备用唯一标识）
- 角色 role ∈ { `CUSTOMER`, `ADMIN` }；账户状态 ∈ { `NORMAL`, `FROZEN` }

### R2 电影（movies）
电影（**电影ID** `movie_id`, 片名 `title`, 导演 `director`, 主演 `actors`, 类型 `genre`, 时长 `duration_minutes`, 上映日期 `release_date`, 参考票价 `base_price`, 简介 `synopsis`, 海报地址 `poster_url`, 上映状态 `showing_status`）

- 主码：movie_id；候选码：（title, release_date）
- 上映状态 ∈ { `UPCOMING`, `SHOWING`, `OFFLINE` }
- **v1.1 变更**：release_date 设为 `NOT NULL`，确保 (title, release_date) 唯一约束对所有记录生效（详见第六节）

### R3 影厅（halls）
影厅（**影厅ID** `hall_id`, 影厅名称 `hall_name` `UK`, 影厅类型 `hall_type`, 排数 `row_count`, 列数 `column_count`）

- 主码：hall_id；候选码：hall_name
- 影厅类型 ∈ { `STANDARD`, `IMAX`, `VIP` }
- 不冗余存储「总座位数」，由 `seats` 实际记录统计，避免与实际座位不一致

### R4 座位（seats）
座位（**座位ID** `seat_id`, 影厅ID `hall_id` `FK`, 排号 `seat_row`, 列号 `seat_column`, 座位类型 `seat_type`, 使用状态 `use_status`）

- 主码：seat_id；候选码：（hall_id, seat_row, seat_column）
- 外键：hall_id → halls(hall_id)
- 座位类型 ∈ { `NORMAL`, `VIP` }；使用状态 ∈ { `ENABLED`, `DISABLED` }（物理可用性，与场次占用状态区分）

### R5 放映场次（screenings）
放映场次（**场次ID** `screening_id`, 电影ID `movie_id` `FK`, 影厅ID `hall_id` `FK`, 开始时间 `start_time`, 结束时间 `end_time`, 语言版本 `language_version`, 字幕 `subtitle`, 场次票价 `ticket_price`, 场次状态 `screening_status`）

- 主码：screening_id
- 外键：movie_id → movies(movie_id)；hall_id → halls(hall_id)
- 场次状态 ∈ { `SCHEDULED`, `SELLING`, `ENDED`, `CANCELLED` }
- 唯一约束 (hall_id, start_time)：同一影厅同一开始时间不能排两场

### R6 订单（orders）
订单（**订单ID** `order_id`, 订单编号 `order_number` `UK`, 用户ID `user_id` `FK`, 场次ID `screening_id` `FK`, 订单总金额 `total_amount`, 下单时间 `ordered_at`, 支付时间 `paid_at`, 订单状态 `order_status`）

- 主码：order_id；候选码：order_number
- 外键：user_id → users(user_id)；screening_id → screenings(screening_id)
- 订单状态 ∈ { `PENDING`, `PAID`, `CANCELLED`, `REFUNDED` }；唯一约束 (order_id, screening_id) 供票表复合外键引用

### R7 电影票（tickets）
电影票（**票ID** `ticket_id`, 票编号 `ticket_number` `UK`, 订单ID `order_id` `FK`, 场次ID `screening_id` `FK`, 座位ID `seat_id` `FK`, 排号快照 `row_number_snapshot`, 列号快照 `column_number_snapshot`, 票价 `ticket_price`, 票状态 `ticket_status`, 出票时间 `issued_at`）

- 主码：ticket_id；候选码：ticket_number
- 外键：(order_id, screening_id) → orders(order_id, screening_id)；(screening_id, seat_id) → seat_occupancies(screening_id, seat_id)
- 票状态 ∈ { `VALID`, `USED`, `REFUNDED` }

### R8 有效座位占用（seat_occupancies）
有效座位占用（**screening_id** `FK`, **seat_id** `FK`, order_id `FK`, occupancy_status, locked_at, lock_expires_at, updated_at）

- 主码：（screening_id, seat_id）组合码
- 外键：screening_id → screenings(screening_id)；seat_id → seats(seat_id)；order_id → orders(order_id)
- 占用状态 ∈ { `AVAILABLE`, `LOCKED`, `SOLD` }
- 约束 ck_occupancies_owner：`AVAILABLE` 时 order_id 必须为空，`LOCKED`/`SOLD` 时 order_id 必须非空

## 三、函数依赖分析

对每个关系模式，依据业务语义列出函数依赖（FD）集合，并判定码。（下列属性名采用中文别名，对应第二节物理列。）

### R1 用户 users
- FD1：user_id → username, password_hash, real_name, phone, email, role, registered_at, account_status
- FD2：username → user_id, phone, …（username 唯一）
- phone、email 虽有唯一约束，但允许为 NULL，因此在当前关系模式中不作为候选码；非空记录可将其视为备用唯一标识
- 候选码：user_id、username；主码选 user_id
- 所有非主属性完全依赖于码，**无部分依赖、无传递依赖**

### R2 电影 movies
- FD1：movie_id → title, director, actors, genre, duration_minutes, release_date, base_price, synopsis, poster_url, showing_status
- FD2：（title, release_date）→ movie_id, …（同片名不同上映日期视为不同影片）
- 候选码：movie_id、（title, release_date）；无部分依赖、无传递依赖

### R3 影厅 halls
- FD1：hall_id → hall_name, hall_type, row_count, column_count
- FD2：hall_name → hall_id, …
- 候选码：hall_id、hall_name；无部分依赖、无传递依赖

### R4 座位 seats
- FD1：seat_id → hall_id, seat_row, seat_column, seat_type, use_status
- FD2：（hall_id, seat_row, seat_column）→ seat_id, seat_type, use_status
- 候选码：seat_id、（hall_id, seat_row, seat_column）；无部分依赖、无传递依赖

### R5 放映场次 screenings
- FD1：screening_id → movie_id, hall_id, start_time, end_time, language_version, subtitle, ticket_price, screening_status
- FD2：（hall_id, start_time）→ screening_id, …（同一影厅同一开始时间只有一场）
- 候选码：screening_id、（hall_id, start_time）；无部分依赖、无传递依赖

### R6 订单 orders
- FD1：order_id → order_number, user_id, screening_id, total_amount, ordered_at, paid_at, order_status
- FD2：order_number → order_id, …
- 候选码：order_id、order_number；无部分依赖、无传递依赖

### R7 电影票 tickets
- FD1：ticket_id → ticket_number, order_id, screening_id, seat_id, row_number_snapshot, column_number_snapshot, ticket_price, ticket_status, issued_at
- FD2：ticket_number → ticket_id, …
- 候选码：ticket_id、ticket_number
- row_number_snapshot、column_number_snapshot 表示**出票时快照**，并非当前 `seats` 表位置的重复列。同一物理座位在重新编号前后签发的历史票可以保留不同快照，因此不存在 seat_id → 两个快照属性的恒定函数依赖
- 所有非主属性直接依赖于电影票候选码，无部分依赖、无传递依赖

### R8 有效座位占用 seat_occupancies
- FD1：（screening_id, seat_id）→ order_id, occupancy_status, locked_at, lock_expires_at, updated_at
- 候选码：（screening_id, seat_id）——组合码
- 非主属性完全依赖于组合码，无部分依赖、无传递依赖

## 四、范式分析（判定至 3NF）

### 4.1 判定依据

- 1NF：每个分量都是不可再分的原子值，无重复组；
- 2NF：在 1NF 基础上，每个非主属性完全函数依赖于码（消除非主属性对码的部分依赖）；
- 3NF：在 2NF 基础上，每个非主属性既不部分依赖也不传递依赖于码。

### 4.2 逐表判定

| 关系模式 | 1NF | 2NF | 3NF | 说明 |
| --- | --- | --- | --- | --- |
| R1 用户 | 满足 | 满足 | 满足 | 单属性码，无非主属性部分/传递依赖 |
| R2 电影 | 满足 | 满足 | 满足 | `actors` 仅作不可检索的展示文本；若需演员级查询应另行拆表 |
| R3 影厅 | 满足 | 满足 | 满足 | 单属性码 |
| R4 座位 | 满足 | 满足 | 满足 | 组合候选码（hall_id,seat_row,seat_column）下非主属性完全依赖 |
| R5 放映场次 | 满足 | 满足 | 满足 | 单属性主码 |
| R6 订单 | 满足 | 满足 | 满足 | 单属性主码 |
| R7 电影票 | 满足 | 满足 | 满足 | 排号、列号为出票时历史快照，直接依赖于票，而非当前座位记录 |
| R8 有效座位占用 | 满足 | 满足 | 满足 | 组合码，无部分/传递依赖 |

**结论**：按当前业务语义，8 个关系模式均满足 3NF。`tickets` 中的排号、列号属于历史快照；`movies.actors` 在当前范围内只作展示文本，不支持按演员检索。

### 4.3 快照字段与演员字段的边界

- `row_number_snapshot`、`column_number_snapshot` 在出票后不可随 `seats` 的重新编号更新，否则会破坏历史凭证语义；二者必须由出票事务从当时的座位记录一次性复制。
- 快照可能与当前座位排号不同，这是预期的历史差异，不是更新异常。
- `actors` 使用逗号分隔文本只适合显示。如果后续出现“按演员检索电影”“维护演员资料”等需求，应新增 `actors` 和 `movie_actors`，而不是继续解析字符串。

## 五、规范化边界与可选扩展

### 5.1 电影票快照不再分解

如果把排号、列号定义为**当前座位位置**，则可从 `tickets` 删除两列，并通过 `tickets.seat_id` 连接 `seats` 获取；该方案结构更简洁，但历史票会随座位重新编号而变化，不符合凭证留存要求。

本系统明确采用历史快照语义，因此保留 `row_number_snapshot`、`column_number_snapshot`。它们由 `ticket_id` 或 `ticket_number` 决定，不由 `seat_id` 单独决定，R7 无需为满足 3NF 而分解。

### 5.2 演员多值属性的可选分解

当前 `movies.actors` 是课程范围内的展示文本。若业务升级为演员级检索，可分解为：

- `actors`（**actor_id**, actor_name, ...）
- `movie_actors`（**movie_id**, **actor_id**, billing_order, role_name）

其中 `movie_actors` 以 `(movie_id, actor_id)` 为组合主码。该扩展能消除演员重复文本，并支持按演员查询；当前没有相应需求，暂不增加额外表，避免扩大项目范围。

### 5.3 实现约束

- 出票时在同一事务内读取 `seats.seat_row`、`seats.seat_column` 并写入票快照。
- 票一旦签发，不允许单独修改快照字段。
- 当前电影主演字段仅用于整体显示；Java 层不提供按单个演员筛选的 DAO 接口。
- 若需求发生变化，A 先更新关系模式和契约，B 再增加演员实体与 DAO。

## 六、完整性约束设计

### 6.1 实体完整性
8 张表均定义主码，主码属性非空且唯一。seat_occupancies 使用（screening_id, seat_id）联合主码。所有主键类型为 `BIGINT UNSIGNED AUTO_INCREMENT`（占用表为组合自然键）。

### 6.2 参照完整性（外键）

全部外键删除策略统一为 `RESTRICT`，业务历史数据（订单、票、场次）不做级联物理删除。（v1.0 前的 `CASCADE`/`SET NULL` 方案已废止。）

| 外键所在表 | 外键 | 参照表 | 删除策略 |
| --- | --- | --- | --- |
| seats | hall_id | halls | RESTRICT |
| screenings | movie_id | movies | RESTRICT |
| screenings | hall_id | halls | RESTRICT |
| orders | user_id | users | RESTRICT |
| orders | screening_id | screenings | RESTRICT |
| seat_occupancies | screening_id | screenings | RESTRICT |
| seat_occupancies | seat_id | seats | RESTRICT |
| seat_occupancies | order_id | orders | RESTRICT |
| tickets | (order_id, screening_id) | orders(order_id, screening_id) | RESTRICT |
| tickets | (screening_id, seat_id) | seat_occupancies(screening_id, seat_id) | RESTRICT |

### 6.3 用户定义完整性（CHECK / UNIQUE）

- 用户：username / phone / email 唯一；role ∈ {CUSTOMER, ADMIN}；account_status ∈ {NORMAL, FROZEN}；
- 电影：**release_date 非空（v1.1）**；duration_minutes > 0；base_price ≥ 0；(title, release_date) 唯一；showing_status ∈ {UPCOMING, SHOWING, OFFLINE}；
- 影厅：row_count > 0；column_count > 0；hall_type ∈ {STANDARD, IMAX, VIP}；
- 座位：(hall_id, seat_row, seat_column) 唯一；use_status ∈ {ENABLED, DISABLED}；seat_type ∈ {NORMAL, VIP}；
- 放映场次：end_time > start_time；ticket_price ≥ 0；(hall_id, start_time) 唯一；screening_status ∈ {SCHEDULED, SELLING, ENDED, CANCELLED}；
- 订单：order_number 唯一；total_amount ≥ 0；order_status ∈ {PENDING, PAID, CANCELLED, REFUNDED}；
- 电影票：ticket_number 唯一；ticket_price ≥ 0；ticket_status ∈ {VALID, USED, REFUNDED}；
- 有效座位占用：occupancy_status ∈ {AVAILABLE, LOCKED, SOLD}；(screening_id, seat_id) 即主码；ck_occupancies_owner 保证 AVAILABLE ↔ order_id 为空、LOCKED/SOLD ↔ order_id 非空。

## 八、AI 辅助说明与人工修改

本阶段先由大模型依据 E-R 图生成关系模式初稿，人工逐项审核后修改：

1. 模型初稿未将 M:N 联系转换为独立表，人工补充第 8 张表「有效座位占用」并设为组合主码；
2. 人工复核后纠正了“seat_id 决定票面排号、列号快照”的错误函数依赖；快照由票决定，R7 在当前语义下满足 3NF；
3. 模型建议直接删除票面排号、列号，人工结合票务凭证留存需求保留历史快照，并补充不可随当前座位编号更新的实现约束；
4. 与成员 B 联合评审后，按接口约定 v1.0 统一复数表名、英文枚举状态、BIGINT UNSIGNED 主键、DECIMAL(10,2) 金额与 RESTRICT 删除策略；本版升级为 v1.1，追加 release_date NOT NULL 与 lock_expires_at 字段。
